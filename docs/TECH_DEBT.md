# Технический долг

## ARCH-001 — Constants audit

### Область и метод аудита

Проверены `00_Constants.js`, `01_LayoutMap.js`, `03_Geometry.js`,
`04_Build.js`, `05_Dropdowns.js`, `07_Calculations.js`, `08_Progress.js`,
`10_Events.js`, `11_Accounts.js`, `12_Utils.js`, `13_Groups.js`, а также
архитектурные правила из `AGENTS.md`, `docs/CODING_STANDARD.md` и
`.github/copilot-instructions.md`. Номера строк относятся к текущему состоянию
файлов на момент аудита. Комментарии и текст сообщений отмечены отдельно от
исполняемого кода.

По правилам проекта Constants должен хранить неизменяемые бизнес- и проектные
значения, а вся геометрия документа должна находиться только в `LAYOUT` и быть
доступна потребителям через Geometry API.

### Геометрия, которую необходимо перенести из `00_Constants.js` в `LAYOUT`

Следующие значения нарушают прямое правило «Constants never store geometry»:

- весь `PASSPORT` (`M4:M9`): адреса ячеек;
- весь `HYP`: число строк гипотез и координаты колонок;
- весь `SPRINT`: число спринтов, шаг в строках и высоты строк;
- весь `MONTH`: число повторяющихся блоков месяца;
- весь `QUARTER`: число строк KPI.

`COLORS`, `BUSINESS`, `SHEETS`, `STATUS` и `RESULT` являются допустимыми
сущностями Constants. После переноса геометрии потребители должны обращаться к
`LAYOUT` через Geometry API там, где требуется вычисление реального диапазона,
а не создавать локальные копии координат.

### Конфликт `PASSPORT` и `LAYOUT.PASSPORT`

| Поле | `PASSPORT` (`00_Constants.js:11–25`) | `LAYOUT.PASSPORT` (`01_LayoutMap.js:65–72`) | Оценка |
|---|---|---|---|
| аккаунт | `ACCOUNT: 'M4'` | `ACCOUNT: "M4"` | Совпадает |
| соцсеть | `SOCIAL: 'M5'` | `SOCIAL: "M5"` | Совпадает |
| сотрудник/ответственный | `EMPLOYEE: 'M6'` | `MANAGER: "M6"` | Конфликт имени при одинаковом адресе |
| год | `YEAR: 'M7'` | `YEAR: "M7"` | Совпадает |
| квартал | `QUARTER: 'M8'` | `QUARTER: "M8"` | Совпадает |
| статус | `STATUS: 'M9'` | `STATUS: "M9"` | Совпадает |

Главный конфликт — публичное имя `EMPLOYEE` против `MANAGER`. Фактическая
модель данных использует `manager` (`11_Accounts.js:131`), а UI называет поле
`Ответственный` (`04_Build.js:160`). Перед удалением `PASSPORT` нужно выбрать и
зафиксировать единую предметную терминологию; механическое переименование может
сломать будущих/внешних потребителей, даже несмотря на отсутствие ссылок в
проверенных модулях.

### Риски удаления и переименования

- Apps Script объединяет файлы проекта в глобальное пространство. Статический
  поиск по заданным файлам не доказывает отсутствие обращений из не включённых
  в аудит модулей, триггеров, библиотек или внешних скриптов.
- Удаление `SHEETS` немедленно сломает загрузку KPI-справочника в
  `03_Geometry.js:54, 57`.
- Удаление остальных объектов до замены дублей закрепит magic values и лишит
  проект single source of truth, даже если текущий runtime не упадёт сразу.
- Переименование ключей — изменение глобального API. Особенно рискованны
  `PASSPORT.EMPLOYEE`/`LAYOUT.PASSPORT.MANAGER`, `STATUS.DONE` при наличии UI-
  термина `'Выполнено'`, а также несовпадение `QUARTER.KPI_ROWS = 11` и рабочих
  диапазонов на 12 строк.
- Одновременное сохранение старых и новых геометрических объектов создаёт два
  источника истины. Переходный период должен быть коротким и проверяемым.
- Замена только текста ошибок или только `getSheetByName` создаст частичную
  миграцию: лист будет искаться по одному имени, а сообщение показывать другое.
- Использование Constants прямо из Calculations для геометрии нарушит слои;
  расчёты должны получать диапазоны через Geometry API.
- В `07_Calculations.js:358–359` уже есть ссылки на отсутствующие в текущем
  `LAYOUT.SPRINT` ключи `STEP` и `HYP_ROWS`. Это отдельный runtime-риск, который
  необходимо разрешить до удаления `SPRINT.STEP_ROWS`/`HYP.ROWS_PER_SPRINT` как
  потенциально задуманных прежних источников этих значений.

### Рекомендуемый порядок миграции

1. Зафиксировать каноническую модель: `MANAGER` или `EMPLOYEE`, 11 или 12 строк
   KPI, а также назначение листа `KPI` относительно `90_DIRECTORY`.
2. Завершить `LAYOUT`: перенести туда недостающую геометрию `PASSPORT`, `HYP`,
   `SPRINT`, `MONTH`, `QUARTER`; устранить отсутствующие ключи `SPRINT.STEP` и
   `SPRINT.HYP_ROWS`, не дублируя вычисляемый шаг.
3. Расширить/нормализовать Geometry API для паспорта, гипотез, KPI и итогов,
   чтобы бизнес-модули не читали координаты напрямую.
4. Перевести потребителей геометрии по одному слою: сначала Builder и
   Dropdowns, затем Calculations, Events, Accounts, Progress и Groups. После
   каждого шага проверять построение шаблона и диапазоны в Google Sheets.
5. Заменить имена листов на существующие `SHEETS.DIRECTORY`,
   `SHEETS.ACCOUNTS`, `SHEETS.TEMPLATE`, включая диагностические сообщения.
   Отдельно решить лист `KPI`, не создавая неверный alias.
6. Заменить бизнес-литералы на `STATUS`, `RESULT` и
   `BUSINESS.PARTIAL_SUCCESS_WEIGHT`; проверить итоги спринта, месяца и квартала
   на данных со всеми статусами и результатами.
7. Заменить существующие дубли палитры на `COLORS`; отдельно спроектировать
   цвета progress bar, которых пока нет в объекте.
8. Повторить глобальный поиск по всему проекту и только после отсутствия
   потребителей удалить геометрические объекты из `00_Constants.js`. Не
   переименовывать ключи и не удалять совместимость в том же изменении без
   отдельной проверки публичного API.
9. Выполнить Apps Script/Google Sheets smoke test: сборка шаблона, создание
   аккаунта, заполнение паспорта, dropdowns, обработка `onEdit`, расчёты и
   группировки. Затем оформить логические изменения отдельными коммитами в
   соответствии с workflow проекта.
